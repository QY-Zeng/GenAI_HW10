基礎 · 問題

LLM 一次只吐一個 token

LLM 回答的方式：看完前面全部的內容，預測下一個 token，接在後面，再預測下一個，直到結束。token 是字或詞的片段。這個迴圈叫自回歸（autoregressive）生成。

Thecatsaton→the→mat→…

（解說）每多生成一個 token，前面的內容就更長一點。如果每一步都把前面整段重看一遍，大量的計算其實是重複的。

基礎 · 沒有快取

沒有快取：每生成一個 token，前面全部重算

不快取時，每一步模型都以整個 prompt 加上已經生成的 tokens 當輸入，attention 需要的資料全部重算。

示意：假想的 4 個 token 的 prompt，每按一次生成 1 個新 token（非實測）

基礎 · 有快取

KV Cache：算過的 K、V 存起來，之後直接用

KV Cache 的做法：每個 token 的 key（K）與 value（V）只算一次，之後重用。

先對整個輸入算好並存起來，之後每一步只計算新 token 的 K、V，附加到快取後面。

（解說）attention 會讓每個新 token 去「查」前面所有 token 的資料，這些資料就是每個 token 的 K 與 V。

Thecatsatonthe
快取裡已有的 K、V這一步才新算的 K、V

基礎 · 為什麼可行

為什麼快取不會改變答案？

在因果（causal）語言模型中，位置 i 的 attention 只依賴它前面的 tokens，所以使用 KV Cache 不影響準確度。

同理，KV cache 只依賴前面的 tokens：只要前面的內容相同，就可以重用。

（解說）用一個畫面理解

Thecatsaton

「on」的 K、V 只看它前面的 The cat sat。之後再接上 the、mat，也不會讓前面已算好的 K、V 改變。這是「跨請求重用」成立的根據。

基礎 · 省多少運算

每一步的運算量，從跟序列長度的平方有關，降到線性

沒有快取

≈ 6nd² + 4n²d

有快取

≈ 6d² + 4nd

n 是序列長度，d 是 hidden size。

（解說）n 越大，兩者差距越大，所以輸入越長、生成越久，快取越划算。

基礎 · prefill 有多慢

長輸入的 prefill 要等好幾秒

輸入 4K tokens、單張 A40：Llama-34B 的 prefill 約 3 秒，Llama-70B 約 6 秒，使用者才會看到第一個字。

代價 · 怎麼管理記憶體

PagedAttention：把作業系統的分頁搬來管 KV cache

把每個請求的 KV cache 切成固定大小的 block，block 不必放在連續的空間。對照：block 像 page，token 像 byte，請求像 process。

做到接近零浪費；吞吐比 FasterTransformer、Orca 高 2–4×（同等延遲）。

block 還能被共享，跨同一請求的序列，甚至跨請求。

跨請求 · 兩種實作

怎麼知道哪些 KV 能重用？hash 鏈與 radix tree

vLLM：Automatic Prefix Caching

每個 block 的 hash 由「父 block 的 hash、這個 block 的 tokens、額外資訊」組成，所以一個 block 的 hash 代表從開頭到它的整段 prefix。

SGLang：RadixAttention

把 KV 留在 radix tree；用 LRU 淘汰最近最少使用的 leaf，每個節點有 reference counter。排程偏好共享最長 prefix 的請求。論文中 page 大小為 1 個 token。

兩者的粒度不同：這裡描述的是論文與文件的設計，不代表現行程式碼的所有細節。

進階 · prefix 不夠用

RAG 的難題：要重用的內容不在開頭

系統提示（開頭，可重用）文件 X文件 Y問題
prefix，可直接重用新算

位置的問題

RAG 把多個檢索到的 chunk 放進輸入，只有第一個 chunk 是 prefix，其他的無法重用。位置編碼又讓 attention states 與位置有關。

品質的問題

直接重用各 chunk 預先算好的 KV（full KV reuse）速度快，卻忽略 chunk 之間的 cross-attention，可能答錯。

進階 · 做法 A

Prompt Cache：把常用文字段做成可重用的模組

用 schema（PML）定義 prompt modules，預先算好 attention states 存起來；論文觀察到 LLM 能處理不連續的 position IDs。

各 module 獨立編碼，跨 module 的 attention 被遮蔽：module 語意獨立時可能無害，彼此相依時品質可能變差。

1.5–10×
GPU 上的 TTFT 改善
20–70×
CPU 上的 TTFT 改善

論文摘要寫的是 GPU 最高 8×、CPU 最高 60×；內文詳細範圍較大，兩者並列時要說明脈絡。

只降 TTFT，不降每個 token 的生成時間：RTX 4090、Llama 7B、3K context，TTFT 從 900 ms 降到 90 ms，每個 token 仍約 32 ms。

進階 · 做法 B

CacheBlend：重用之後，只重算一小部分

重用預先算好的 KV cache，再「選擇性重算」少數影響最大（KV deviation 高）的 token；預設約 15%，重算與載入下一層 KV 同時進行，所以不增加延遲。

實務 · API 的 prompt caching

在 API 裡用快取：怎麼命中、怎麼算錢

  • 快取到 cache_control 指定位置為止的完整 prefix，順序是 tools → system → messages。
  • 預設壽命 5 分鐘，命中就免費刷新；可選 1 小時。
  • 價格：5 分鐘寫入 1.25×、1 小時寫入 2×、讀取一般 0.1×（部分模型更低）。
  • 最小可快取長度依模型而異，512 到 4,096 tokens；太短就不快取，也不會報錯。
  • prefix 必須 100% 相同；最多 4 個明確 breakpoint；快取不影響輸出。

檢查清單（解說）

  • 不變的內容放最前面：tool 定義、系統指示、長文件。
  • 會變的內容（時間戳、使用者問題）放最後；breakpoint 放在最後一個穩定的區塊。
  • 看回應的 usage 欄位確認有沒有命中，不要假設。
  • 請求間隔可能超過 5 分鐘時，評估 1 小時壽命。

價格與限制會變，以官方文件為準（取得日 2026-11-15）。

整理 · 自我檢查

學完了嗎？點開看答案

為什麼使用 KV cache 不會改變模型的答案？

因果語言模型中，每個位置的 attention 只依賴它前面的 tokens，前面的 K、V 不會因後面新增的 token 而改變。

KV cache 的代價是什麼？

GPU 記憶體。每個 token 都要存 K、V，所以長 context 與大量併發請求會吃掉很多記憶體，要靠 PagedAttention 這類方式管理。

prefix caching 為什麼只能重用「開頭」？

KV 取決於前面的內容；只有開頭相同，後面每個 token 的 K、V 才會一樣。內容出現在中間時，它前面的內容不同，K、V 就不能直接沿用，需要 Prompt Cache、CacheBlend 這類方法。

Prompt Cache 和 prompt caching 差在哪？

前者是論文提出的非 prefix 重用系統，後者是商用 API 的 prefix 快取功能。
