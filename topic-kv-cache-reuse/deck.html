背景與痛點

為什麼 Prefill 是推理系統的頭號瓶頸？

02 / 12

Prefill（預填充階段）— 計算密集瓶頸

  • 一次處理完整輸入上下文，計算複雜度隨序列長度呈二次成長。
  • 以 4K tokens 為例，在單張 A40 GPU 上即需 3–6 秒（Llama-34B／70B）[CacheBlend, §2, p.3]。
  • Prefill 干擾（Prefill Interference）：長 Prefill 不只直接拉高 TTFT，還會搶佔排程波及正在 Decode 的請求，拖累 TBT／ITL 與 E2E，壓低滿足 SLO 的有效吞吐 Goodput [DroidSpeak, §2.1, §2.3, Fig. 5, p.3–4]。

Decode（解碼階段）與傳統 Prefix Caching 枷鎖

  • Decode 階段：利用 KV Cache 逐 token 生成，屬記憶體頻寬受限且複雜度僅呈線性成長 [DroidSpeak, §2.1, Fig. 3, p.2–3]。
  • 傳統推理引擎（vLLM／SGLang）的 Prefix Caching 雖免重算前綴，但受限於三重枷鎖：
🔒 同一模型
換微調或尺寸即失效
🔒 同一 GPU
HBM 滿了只能驅逐
🔒 嚴格前綴
非前綴拼接即 miss
問題核心：只要實際應用涉及多區塊拼接（RAG）、跨機卸載、多代理接力或多模型路由，傳統 Prefix Caching 就會失效並退回昂貴的全量 Prefill [CacheBlend, §3.2, p.3; LMCache, §1, p.1]。

里程碑 1 · EuroSys '25

CacheBlend：RAG 多區塊融合與 HKVD 選擇性重算

04 / 12

三大關鍵設計：速度媲美全重用、品質對齊全重算

  1. HKVD 選擇性重算＋漸進過濾：受惠於注意力稀疏性，僅需重算每層約 10–15%（實測 5%–18%，系統保底 15%）高偏差 tokens，首層全算後逐層過濾 [CacheBlend, §4.3, §5.1, §7.3, Fig. 6–9, p.6–8, 12]。
  2. RoPE 單次旋轉校正：利用相對距離不變性，一次性乘法對齊非前綴位置 [CacheBlend, Footnote 3, p.6; Appendix A, p.16]。
  3. 計算–載入逐層管線化：重疊第 i 層重算與第 i+1 層 SSD／RAM 載入，讓重算延遲被載入時間隱藏 [CacheBlend, §5.1, §6, Fig. 10–11, p.8–9]。

直覺案例：為何 Full KV Reuse 會答錯？

里程碑 2 · 企業級系統層

LMCache：走出單張 GPU 的企業級 KV Cache 層

05 / 12

三大系統工程支柱

  1. Chunk 批次搬運（預設 256 tokens）：以客製 CUDA kernel 聚合成連續 streaming buffer 再由 DMA 搬運，CPU 載入頻寬達 400 Gbps（較 vLLM 原生 88 Gbps 快 4.5×）[LMCache, §5.1, §8.6, Table 5, p.6, 13]。
  2. 雙層管線＋零複製：逐層 CUDA stream 重疊＋排隊非同步預取（E2E 降 1.46×），搭配參考計數 Zero-Copy 與三指標 Dynamic Offloading [LMCache, §5.2–5.3, §8.6, Fig. 7, 13, p.6–8, 14]。
  3. 雙標準化介面：KV Connector API（獲 NVIDIA Dynamo、llm-d、AIBrix、KServe 採用）＋ Controller API（lookup/move/pin/compress）[LMCache, §6–7, Table 2–3, p.8–10]。

生產實戰教訓

企業生產現場的兩個反直覺真相（LMCache）

06 / 12

真相一：遠端儲存竟比 Prefill 快——但有交叉點！

  • 現代高速物件儲存（如 S3 Express）讓 Company C 直接從遠端載入 KV 反而比完整 Prefill 降低 22–32% TTFT [LMCache, §9, p.15]。
  • 前提邊界（B200 敏感度分析）：若網路頻寬僅 32 Gbps，唯有輸入超過 256K tokens 載入才勝過重算；達 64–128 Gbps 才全序列長度皆勝出 [LMCache, §8.7, Fig. 15, p.14–15]。
工程啟示：不可盲目一律載入，系統必須依網路頻寬與上下文長度做自適應載入決策。

真相二：截斷對話開頭，反讓快取命中率直接腰斬！

  • 工業界常見滑動視窗 Context Truncation（僅保留最新 tokens）會破壞前綴雜湊匹配。
  • Company F 真實流量實測：截斷後前綴快取命中率從 ~85% 暴跌至 ~45% [LMCache, §9, p.15]。
工程啟示：長對話與代理系統應盡量採 append-only 上下文管理以保護前綴快取。
真實企業流量回放（Company F & G）：導入 LMCache 後，高 QPS 下 TTFT 降低 3.7–6.8×、ITL 降低 19%–58% [LMCache, §8.3, Fig. 9–10, p.12]。

里程碑 3 · 多代理動態接力

RelayCaching：化解多代理系統 O(M²) 級聯冗餘

07 / 12

問題與層×Token 雙維稀疏修正

  • 痛點：Architect → Developer → Reviewer 接力時，上游動態輸出嵌入下游不同角色提示（prefix variation），累積 Prefill 成本呈 O(M²) 暴增 [RelayCaching, §1, Fig. 1, p.1–2]。
  • 六模型（0.6B–32B）三大規律：Key/Value Norm 皆 >0.92，唯獨 Value Cosine（0.800） 為主導偏差；層間呈 U 型曲線（僅中層偏差大）；相鄰層 Spearman 相關迅速穩定 > 0.9 [RelayCaching, §3.1–3.3, Fig. 2–4, p.3–4]。
  • 精準修正：跳過淺／深層，僅於中層 [L_start, L_end] 與偵測層 L_det 採用偏差（1.5×均值）∪ 注意力影響力（1.45×均值）∪ 尾端 10 tokens 三合一篩選（GSM8K 消融：僅偏差 79.68% → 三合一拉回 84.84%）；目前限同質多代理（同架構同權重）[RelayCaching, §4.2–4.3, §5.4, Table 3, App. C, p.5–8, 18]。

里程碑 4 · 同底模跨模型

DroidSpeak：同底模微調模型間的連續層選擇性重算

08 / 12

跨微調模型洞察與 E-Cache 切換陷阱

  • 全盤重用崩潰：同底模微調變體若直接全用 baseline KV，HotpotQA 損失 >50% F1 [DroidSpeak, §3.2.1, Fig. 6, p.4–5]。
  • 僅 11% 為關鍵層：平均僅 11% 層對微調敏感（單層重用掉 >10% F1）[DroidSpeak, §3.2.2, Fig. 7, p.5–6]。
  • 為何不能散落重算？每次從「重用」切回「重算」皆須傳送 baseline E cache（體積達 KV 的 2× 至 GQA 70B 的 4×），且多次載入會放大累積誤差 [DroidSpeak, §4.1, Fig. 9–11, p.6–7]。
  • 兩階段設計：採 recompute → reuse → recompute → reuse 限制至多 1 次切換；離線 50 筆 HotpotQA 剖析帕累托前緣（跨資料集平均差僅 2 分 F1），線上依延遲 SLO 動態調整 [DroidSpeak, §4.2–4.4, §5.1, §5.5, p.7–11]。

里程碑 5 · 跨尺寸免重算

Cross-Model KV Transfer：跨尺寸模型的閉式線性映射

09 / 12

三步驟無梯度閉式 Ridge Mapper

針對同家族、dense full-attention 且 Matched-KV（KV 頭數 8、單頭維度 128 相同）配對，跨模型 KV 常具顯著線性結構（Qwen3 14B→32B 單層解釋 K 56%、k=8 層達 79%）[Cross-Model KV, §2.1, §2.3, §5, Table 7, p.2–4, 9, 14]。

  1. 跨層 top-k 源層選擇：消融貢獻最大（k=8→1 使 GSM8K 從 90.98% 崩至 0.38%）[§3.2, §4.3, Table 2]。
  2. 無位置內容空間映射：剝除源 RoPE → 映射 → 重施目標 RoPE，泛化至 32K 長文 [§3.3, p.5]。
  3. 逐頭嶺回歸閉式解：500 條 FineWeb-Edu 序列於 8×H100 約 47–87 分鐘擬合，免反向傳播；Mapper 佔 4–12 GB [§3.1, Table 12, App. E]。

分層結果：Tier 1 亮眼 vs. Tier 2 靠 MLP 救援

  • Tier 1（4 組高保真）：平均保留 73–98%（Qwen3 14B→32B 97.6%、Llama 3.1 8B→70B 72.8%）；S→L 加速 2.7–25.1×（Qwen3 14B→32B 於 32K 為 278 ms vs 6,975 ms = 25×），CoQA 10 輪穩定 [§4.2, §4.6–4.7, Table 1, 5, 16]。
  • Tier 2（2 組線性失敗）：Ministral 3B→14B（44.2%）與 8B→14B（41.6%）退化；換用 2 層 MLP 救回 +24.3 至 +36.8 pp（HellaSwag 全破 90%）[§4.2, §4.4, Table 1, 3]。

跨篇技術串聯

貫穿五篇的兩條隱藏主線：RoPE 對齊與誤差落點

10 / 12

主線 A｜RoPE 旋轉位置編碼對齊三部曲

  1. CacheBlend：預存 K 向量乘上一次相對旋轉矩陣，近零開銷恢復非前綴位置 [CacheBlend, Footnote 3, App. A]。
  2. RelayCaching：上游直接存 Pre-RoPE KV，下游接力 Prefill 時再重施目標位置 RoPE [RelayCaching, §4.2, Fig. 5, p.5]。
  3. Cross-Model KV Transfer：於無位置內容空間完成線性映射，徹底解耦位置與語意 [Cross-Model KV, §3.3, §4.3, Table 2]：
K̂_t = ( K_s · R⁻¹_Θs(t) · W_K + b_K ) · R_Θt(t)
消融警示：若推論時遺漏重施 RoPE，Qwen3 14B→32B 的 MMLU 崩跌至 25.79%、GSM8K 崩跌至 4.17% [Table 2, p.7]。

主線 B｜偏差指標進化：誤差「落點」> 誤差「大小」

  • 跨 12 組 matched-KV 配對評估，校準集重建指標 R²_K 與 HellaSwag 保留率毫無正相關（Pearson r = −0.20）[Cross-Model KV, §4.5, p.7–8]。
  • 真正決定下游表現的是 Attention-Output Cosine（r = +0.57）——因為注意力只讀取目標 Query 敏感子空間。
  • MLP 救回 +37 pp 的關鍵，在於大幅降低 K-concentration（Δ ≈ −2.5），將殘差推離注意力讀取方向 [Table 4, p.8]。

跨文獻張力並陳

別只看單篇結論！四大跨文獻張力與前提邊界

11 / 12

⚠️ 張力 1｜靜態 RAG vs. 動態 MAS

CacheBlend 在靜態 RAG 品質損 ≤ 0.02；但 RelayCaching 將其移至動態多代理時 GSM8K 跌至 74.73–77.56% 且 12K 呈線性膨脹（1.08 s vs 0.42 s），因解碼重用主導偏差為 Value Cosine（0.800） 而非 Value Norm（0.926）[CacheBlend, §7.2; RelayCaching, §3.1, §5.2–5.3]。

⚠️ 張力 2｜同架構重算 vs. 跨尺寸映射

DroidSpeak 不假設線性但限同架構（1.7–2.6×）；NVIDIA Ridge 跨尺寸最高快 25×，但在 Ministral Tier 2 五基準平均跌至 41.6–44.2%，須改訓練 MLP 救回 HellaSwag 至 92–96% [DroidSpeak, §3.1, §5.2; Cross-Model KV, §4.2, §4.4, Table 1, 3]。

⚠️ 張力 3｜重建誤差 R² vs. 子空間保真度

R² 適合單配對挑選源層，跨配對評估卻完全失靈（r = −0.20）；必須改看 Attention-Output Cosine（r = +0.57） 與 K-concentration（誤差是否落在 Query 讀取方向）[Cross-Model KV, §4.5, Table 4]。

⚠️ 張力 4｜遠端卸載交叉點與截斷反噬

高速物件儲存降 22–32% TTFT，但 32 Gbps 低頻寬下須 >256K tokens 才勝過重算；滑動視窗截斷則讓前綴命中率從 ~85% 腰斬至 ~45% [LMCache, §8.7, §9, Fig. 15]。
